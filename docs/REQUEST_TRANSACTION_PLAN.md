# 请求事务与连接资源：诊断结论及实施条件

日期：2026-10-11；ARCH-12 评估范围。实测和自审见[记录188](reviews/2026-10-11-implementation-188-request-transaction-assessment.md)。

## 1. 当前结论

**保留当前请求事务，不立即加入连接池或分阶段事务。** 无连接限额的合成对照没有证明吞吐/时延收益；额外建连有成本。人为设置4个连接槽时出现收益，证明拆分可以缓解连接受限情形，不能据此认定现网已经受限。后续用实际请求的连接等待、并发和可用资源证明必要性，再实施。

另须核验最终输出的权限和事实新鲜度：长事务不等于授权一直有效。诊断证明撤权、归档、完整性变化和停用身份能在等待期间提交；再次查询能够发现变化，Python中的旧证据不会自动清空。**记录188当时没有实现生产最终输出栅栏，也没有证明所有入口已能拒绝中途变化。** 2026-10-12已由[记录191](reviews/2026-10-12-implementation-191-final-output-validation.md)完成实际入口复现与修复，契约见[最终输出复核](FINAL_OUTPUT_VALIDATION.md)。保留现有事务，性能拆分仍不得绕过授权、预算、持有权及恢复约束。

## 2. 现在如何持有连接

| 入口/职责 | 当前行为 | 拆分必须保留的约束 |
| --- | --- | --- |
| [ProductionRuntime](../src/medops/bootstrap/runtime.py) | 每次connection新建app LOGIN连接；在事务中yield，成功提交、异常回滚 | 独立角色、SET LOCAL部门上下文；任何新连接重新绑定 |
| [Ask](../src/medops/api/routes/ask.py) | 身份→发布策略→Harness检索/模型/核验→Trace/可选加密材料，都在同一个请求事务 | 策略固定；审计提交后才释放答案；不得重跑模型弥补存储错误 |
| [TaskRunner](../src/medops/application/tasks.py) | 领取是短事务；业务另一个长事务；调用前独立查租约；结果与审计一并写入；失败用新连接报告 | attempt/租约/数据库时钟不变；失租者不能覆盖新结果；已发生费用保留 |
| [节点账本](../src/medops/harness/executions.py) | claim、attempt、complete/fail在调用方事务，依赖唯一键和行锁 | 释放事务改变claim可见性/回滚方式，必须定义独立执行意图和恢复协议 |
| [RetrievalServices](../src/medops/bootstrap/retrieval.py) | 工厂复用调用方绑定的连接；SQL回查、翻译等待和本地推理仍受外层事务覆盖 | 候选不是事实；缓存命中也必须事实回查；不得在线程间复用同一连接 |

`statement_timeout`限制SQL，不能取消外部HTTP或本地设备等待。整个执行的时间/Token/费用限制继续由Harness和共享执行预算负责，不新增或扩大额度。

## 3. 数据库语义与真实诊断

在PostgreSQL默认`READ COMMITTED`下，每条查询取其开始时的已提交快照；同一个事务的后续查询可能看到已经提交的变化。它不会自动更新已返回Python的对象。[PostgreSQL 17事务隔离](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)

事实读取持有的表级`ACCESS SHARE`锁会阻挡`ACCESS EXCLUSIVE`，不会阻挡普通ACL删除/状态更新所需的表锁。因此不能从“事务还没结束”推导出“撤权要等回答结束”。[PostgreSQL 17锁兼容关系](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-TABLES)

实测使用真实`ProductionRuntime.connection()`、真实迁移到0025的临时库、app LOGIN、FORCE RLS、目录、事实回查和operation key写入；不加载BGE、不调用API。两臂都做最终身份/完整Evidence比较，中间用250ms sleep模拟外部等待：

- held：初读/claim、等待、终检/complete，只有一个事务。
- phased：初读/claim提交并关闭连接；等待；新连接重新解析身份/绑定部门/终检/complete。
- 8并发、每臂24次、3轮交替先后，无限额与人为4槽各测一次；合计12臂、288次合成执行。
- 10ms采样`pg_stat_activity`，只取本臂独有application_name的数量/状态/锁等待，不采集SQL正文或连接凭据。均值是采样观察值，峰值是下界。[PostgreSQL 17活动监测](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)
- “租用ms/请求”从获得可选槽后开始，包括连接建立、SQL、关闭；phased汇总两次租用，等待槽耗时计入端到端耗时。

逐臂数字和三轮中位摘要见[机器结果](reviews/2026-10-11-implementation-188-results.json)。合成槽不等于已部署连接池；测试库隔离但共享宿主资源，小样本P95不用于真实问答验收、容量上限或质量改进声明。

锁与变化诊断同时验证：`ACCESS EXCLUSIVE NOWAIT`在持有事实读事务时得到`55P03`，事务结束后成功；ACL删除可在长事务期间提交；再次回查不可见。归档、来源未验证、内容哈希损坏分别被事实回查拒绝；身份停用时目录返回无用户，**只回查证据仍可得到同一证据**，所以身份与事实两者都要核验。

## 4. 先补输出复核，再考虑拆分

ARCH-15的建议范围：

1. 在Ask、五类异步Skill及MCP实际输出边界复现：用暂停的假网关/真实本地库，在检索后、生成/判定中和持久化前提交撤权、归档、来源异常或身份变更；不产生托管费用。
2. 确定输出所依赖的完整证据集合：全部共同必需块，不只检查最后列出的Citation；结构化第二阶段仍要核验其依据。用户叙述与文档事实保持区分。
3. 最终重新解析身份、当前角色/scopes及ACL；核对完整Citation、实际文本和哈希、文档状态/生效窗口、来源完整性与parse质量。任何变化失败关闭，不能静默删掉必要证据后继续输出旧结论。
4. 明确最终检查与提交之间的授权线性化点，不能只有一个SELECT却宣称消除了检查后变化的竞态。评估窄权限锁定函数或受控写入版本栅栏，覆盖官方ACL/归档/身份/来源写路径；固定锁顺序、期限及失败行为。不能给app角色通用UPDATE或改用admin DSN。
5. 成功结果与Trace、Escalation及配置启用的加密材料仍一次原子提交；拒绝/失败不能丢弃费用回执、失租事实或已记录调用，也不能自动付费再生成。各入口对外错误/升级口径一致。

当前[ACL变更](../src/medops/ingestion/acl.py)先锁document行，归档/发布也按受控事务处理；直接把所有表锁住会使全局写入竞争扩大。最终锁方案必须验证具体写路径、直接数据库运维的边界及最小权限，而不是直接扩权。

## 5. 条件满足后的分阶段方案

### A：短读阶段

验证token/目录、注入事务本地部门，选定发布策略/灰度、固定QueryContext。创建执行意图，绑定trace/run/attempt、主体/权限指纹、模型/Prompt/Skill/检索配置版本、输入/代码摘要及预算profile；正文只进现有受限加密存储。检索SQL取候选并做事实回查；连接关闭后只能持有候选或有版本的证据快照。

检索自身还有embedding、翻译、重排：先算不依赖事实库的工作；词法/向量查询使用短身份事务；local rerank在事务外；返回前按同一截止时间终检。先确定策略/词表和事实变化处理，不能随中途发布切换参数。没有测得收益的双连接通道不重新接入。

### B：外部计算阶段

模型及本地推理不占事实库连接；预算、调用回执、取消、翻译收束和Task调用前租约检查保留。独立短事务账本提交claim/attempt的可见状态，必须支持唯一键、claim_no、过期恢复及结果重用；只有模型版本标签或memory checkpoint不够。失败/未知费用保守留存，不把未知标0。

### C：最终授权/事实复核与提交

新app连接重新解析身份/绑定部门；核对同一意图/Task lease/attempt和所有依赖事实，经ARCH-15验证的栅栏确定授权点；状态或哈希变化则拒绝/升级。结果、审计、受限材料、意图完成状态原子写入。只有提交成功才释放输出。报告失败用独立恢复事务；不在已中止事务上继续查询。

## 6. 为什么现在不直接引入Pool

| 选项 | 可能价值 | 本轮结论/限制 |
| --- | --- | --- |
| 保留现有每请求连接 | 少一次建连，原有账本/审计语义简单 | 当前采用；不能声称自动解决新鲜度 |
| 只加连接池，仍每请求长事务 | 可减少连接建立成本、约束最大后端数 | 外部等待期间仍占pool槽；队列可能增加。没有隔离测得连接建立收益，不采用 |
| 短事务+每阶段新连接 | 释放模型等待期间的DB连接 | 无槽限制未证实收益；需要完整执行/恢复/权限协议，本轮仅原型 |
| 短事务+有界池 | 同时减少建连与持有时间 | 后续独立测量；连接reset、失败回收、等待期限、跨部门复用及Task独立租约通道必须回归 |
| 外部连接代理/独立服务 | 部署侧集中管理连接 | 引入新的故障/身份上下文/运维边界；此轮无理由扩展部署 |

## 7. 再次启动性能实施的证据

在实际运行环境记录请求等待建连/取槽、连接持有时间、idle-in-transaction、锁/死锁、客户端后端数、最老事务、租约/预算账本通道失败与实际吞吐；只留元数据。先做无模型诊断，再经当次授权做真实问答配对。

满足实际连接瓶颈证据、最终授权栅栏与恢复契约测试后，分别比较原行为、只加池、只拆事务及组合。报告Recall/支持/完整性/拒答、安全、P50/P95、吞吐、连接时间和费用，不改原门槛。任何结果不满足就拒绝上线；不能把合成4槽的收益外推为真实API提速。
