# 历史查询执行契约（ARCH-02）

更新：2026-10-11。实现、自审、迁移及回归见[记录 178](reviews/2026-10-11-implementation-178-historical-query-context.md)。这是 Ask、异步 Skill 与单条 Ask Replay 的执行输入修复；Agent、Skill 最终业务判断和完整原条件回放仍按台账推进。

## 1. 日期与历史模式

传输无关的 `QueryContext` 保存两个字段：

| 字段 | 含义 |
| --- | --- |
| `as_of` | 本次执行采用的生效日期；每次执行解析一次，多个节点/批内 Skill 共同沿用 |
| `historical_requested` | 是否由调用者显式选择历史查询；普通请求即使测试时钟固定在过去，也不会开启归档访问 |

显式请求的原始有效选择器可由 `context.selector` 得到 `{"as_of": "YYYY-MM-DD"}`；未显式请求返回 `None`。空字段和对象键次序不改变其含义。正常请求使用 runtime 固定的测试日期或执行开始时的 `date.today()`；异步普通任务在**执行时**解析日期，历史任务则保留提交时提供的日期。日期是文档生效期的日历日期，沿用既有规则，不提供日期内某时刻的事实快照。

支持的请求示例：

```json
{"query": "根据指定说明书核对其文字内容", "historical": {"as_of": "2025-01-01"}}
```

Task 在原 `skill_name`、`skill_version`、`input` 外带相同的 `historical` 对象。未带该对象则是普通查询。

`version` 字段为保持请求形状兼容而保留，但 **Ask/Task 的裸版本选择器尚未实现**。同名 `v1` 可能属于不同文档家族；它不能被猜成当前版或解析为日期。两个入口均返回 HTTP **400 / invalid_request**，提示使用 `historical.as_of`；旧队列中遗留的版本任务也会在装配前失败，不调用模型。不合法的请求结构仍由 API Schema 返回 422。未来精确版本选择需同时定义文档/家族身份、唯一性、可见性与生效期规则，再增加能力。

## 2. 完整传递路径

| 环节 | 规则 |
| --- | --- |
| Ask | 选择器解析后写入依赖和 Harness 状态；冲突的日期/模式在模型调用前拒绝 |
| Task / Skill | 队列保存原选择器；worker 装配同一日期给词法、向量、来源解析和引用事实回查；Registry 固定执行上下文 |
| `label_query` | Harness 初始状态携带历史上下文；最终片段、引用和历史提示保留 |
| 结构化 Skill | 第一阶段 Harness 沿用上下文；`off_label_check` / `protocol_deviation` 最终结果保留历史提示，最终业务判断可靠性另由 ARCH-03 验证 |
| `citation_verification` | 历史引用回查也显式允许归档；每条事实仍过 RLS、生效期、完整性与解析信任检查；结果有历史提示 |
| `ae_extraction` | 从用户叙述提取，不检索文档；不会因请求带历史日期而声称用了历史文档 |
| 批量 Skill | 分发子任务前固定日期，避免跨午夜时同一批的节点采用不同日期 |
| 缓存 / operation key | 日期和显式历史模式均参与隔离；同一日期的普通与历史请求不能互用候选缓存或节点结果 |
| Trace / 受限载荷 | Trace 新增严格类型的日期/模式元数据；受限 input 载荷也保存同一上下文。正文、证据、模型输出的加密/保留/访问规则不变 |

历史访问只扩展文档状态候选到 `active + archived`，并保持 `effective_from <= as_of < effective_to`（没有结束日期时不限制右边界）。**生效日可用，失效日不可用**。draft、withdrawn、未授权、来源完整性失败、低信任解析仍不能成为证据；指定来源匹配和聚焦候选也按同一天选文档。只有实际使用归档证据才设置 `historical_notice=true`，不能因日期早或请求带历史对象就自动设置。

## 3. Replay 的准确含义

单条管理员 Replay 仅支持 **Ask Trace**：保存原查询日和原显式历史模式，在原主体的**当前身份/部门/权限**下执行，使用**当前事实、当前发布/灰度策略**，并生成全新 Trace/run/operation key。两侧报告均给出 `query_context`。

普通 Ask Replay 也沿用记录的生效日，但仍只允许 active 文档；它不会把后来归档的文档当作当前可用文档。显式历史 Replay 允许当日有效的归档文档，仍不能绕过今天的撤权、撤回或完整性限制。

以下情况在任何模型调用前拒绝：

- 旧 Trace 的 `query_context` 是 NULL：原输入未知，不把它补成普通模式或今天。
- Task/MCP Trace：摘要中的 query 不是完整业务输入，不能拿 Skill 名或工具名称当作问题运行。
- 原主体不再存在，或其部门改变；不存在的 Trace 和 Replay 的 Replay 保留既有 404 行为。
- 状态、依赖与保存的查询上下文冲突。

记录 178 当时只修复日期/显式模式；那份结果不是原条件复现。后续 ARCH-07 已补新版 Ask 的完整输入/session entities 与实际模型/渲染记录，见[执行记录与回放契约](EXECUTION_REPLAY.md)。诊断仍使用当前事实和策略；原条件模式缺少归档语料、索引及可验证旧运行工件，明确拒绝，不根据保存的模型输出或证据推断原条件已恢复。

## 4. 兼容、部署与回滚

1. migration **0024** 为 `traces` 增加 nullable `query_context` JSONB；仅允许 `as_of` 字符串和 `historical_requested` 布尔两个键。没有改权限、事实索引或存量正文。旧行保持 NULL，不伪造输入。
2. 部署顺序为先迁移数据库，再更新 API/worker/MCP；新 Trace store 使用该列，未迁移的环境不可启动新代码进行业务运行。本轮本机三库迁移情况见记录 178；其他环境需自行升级。
3. `ReplayReport` 新增两侧的可空 `query_context`，请求说明同步导出到公开 Schema/OpenAPI；这是可选的附加元数据。Ask/Task 的字段形状不变；日期拒绝数字、非规范日期和时间戳的隐式转换。Skill 输出共享默认值 `historical_notice=false`。强类型客户端若禁止未知响应字段，需要更新生成的模型；新增字段不保证这类旧客户端直接兼容。
4. 旧代码兼容新增 nullable 列；代码回滚可保留 0024。数据库降级会删除新上下文，必须先停写并导出所需 Trace 元数据；不能靠降级恢复本来没有记录的旧输入。
5. 常驻服务需更新/重启才加载新代码。本轮工程检查和迁移不代表真实模型质量或性能复测，实际费用运行仍需单独授权。
