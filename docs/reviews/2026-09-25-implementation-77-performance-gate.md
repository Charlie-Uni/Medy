## 1. 方法

- **被测对象**：生产运行时的真实进程——`python -m medops.api.serve --device mps`（单个 uvicorn 进程，同步端点走 anyio 线程池，嵌入与重排共用一条钉住的模型线程，记录 54 §3.0）与 `python -m medops.worker.serve --device mps`（单 worker）。身份用记录 67 的合成签发方，部门 MA。
- **问题集**：`queries.json`——从主集 v2 全量运行的 MA 部门样本抽取（种子 20260925），每级 24 条「已回答且引用 gold」+ 6 条「证据不足升级」，**四级互不重复**：`c1-cold`（并发 1，新进程首批）、`c2`、`c4`、`c1-warm`（并发 1，重复 c1-cold 的 30 题）。规则拒答（0 次模型调用、毫秒级）刻意不放进来，以免拉低 P95。
- **复杂 Skill**：8 个 `label_query@1.0.0` 任务经 `/v1/tasks` 入队，API 停机后由一个 worker 顺序执行（本机只有一个 Metal 设备）。Skill 时延取 `task_attempts` 的执行时间；排队等待单列（取决于 worker 数而不是 Skill）。
- **判据**：客户端墙钟时延，最近秩百分位（P95 = 第 ⌈0.95n⌉ 小）；失败 = HTTP 非 200 或 `system_failure` 升级；证据不足升级与拒答是正常结果，计入时延不计入失败。
- **归因**：工具内置 OTLP/HTTP 接收器，API 以 `OTEL_EXPORTER_OTLP_ENDPOINT` 指向它；每个请求的 `http.request` / `harness.node` / `retrieval.fact_plane` / `retrieval.rerank` / `llm.call` span 按 `medops.trace_id` 归并（`spans.jsonl` 入库供复核）。服务代码未为测试改动。
- **不入库**：进程日志（`api.log` / `worker.log`，已加 `.gitignore`）。DSN、令牌只在进程环境里。

## 4. 归因（服务端 span，秒）

### 4.1 每级各段时延（p50 / p95）

| 级 | 事实平面（词法+向量+复核） | 重排（含钉住线程排队） | retrieve 节点合计 | 回答调用 | 判定调用 | 判定次数 / 请求 | http 合计 |
| --- | --- | --- | --- | --- | --- | ---: | --- |
| c1-cold 重跑（并发 1，新进程） | 0.17 / 0.89 | 2.41 / 7.16（max 14.5） | 2.74 / 7.58（max 18.1） | 2.76 / 5.08（max 9.0） | 2.23 / 3.21 | 0.93 | 8.01 / 16.95 |
| c1-warm（并发 1） | 0.18 / 0.65 | 2.31 / 3.10 | 2.56 / 3.32 | 2.46 / 6.63（max 10.0） | 2.09 / 3.99 | 0.90 | 7.53 / 12.75 |
| c2 | 0.60 / 3.36 | 2.60 / 5.03 | 3.40 / 8.40 | 3.04 / 5.71 | 2.03 / 3.93 | 0.90 | 9.53 / 15.92 |
| c4 | 4.16 / 11.01 | 7.89 / 14.97 | 12.54 / 18.90 | 2.56 / 4.50 | 2.21 / 3.31 | 0.87 | 17.84 / 23.43 |
| 任务（worker） | 0.14 / 0.88 | 2.01 / 2.24 | 2.21 / 2.82 | 3.13 / 5.52 | 2.73 / 3.83 | 1.12 | — |

读法：

- **并发 1 的 P95 主要是模型调用的尾部**：回答调用 p95 6.6 秒（max 10 秒），加一次判定 2–4 秒，再加检索 2.6–3.3 秒。即使重排为零，P95 也在 10 秒上下——8 秒门禁对「两次 gpt-6-sol 调用 + 本地重排」的链路本身就很紧。
- **并发 > 1 时瓶颈换成钉住的模型线程**：重排在 c4 从 2.3 秒涨到 7.9 秒（p50），事实平面从 0.18 秒涨到 4.16 秒——不是数据库变慢，而是查询嵌入（本身 40 毫秒）排在别人 6 秒的重排后面。一个进程的重排能力约 0.2–0.4 次/秒，就是吞吐上限 0.21 req/s 的来源。
- 冷热差异（同一批 30 题，新进程 vs 同进程重复）：P95 16.95 → 12.76 秒，P50 8.01 → 7.53 秒。差异来自重排的尾部（冷 p95 7.2 秒 / max 14.5 秒，热 p95 3.1 秒——同一题在同一进程里第二次只要 1/3 的时间，Metal 内核与权重页已热）和事实平面首批（0.4–1.4 秒 → 0.18 秒）；模型调用不受冷热影响。新进程的第一次重排 1.9 秒（重跑）到 8.5 秒（冒烟，20 对满载）不等。

### 4.2 重排的离线微基准（20 对真实 chunk，平均 491 字，同一机器）

| 设备 | 精度 | batch | 三次调用（秒） |
| --- | --- | ---: | --- |
| mps | fp32 | 8 | 6.93 / 6.60 / 6.52 |
| mps | fp32 | 20 | 6.97 / 6.60 / 6.58 |
| cpu | fp32 | 8 | 9.47 / 7.58 / 7.07 |
| cpu | fp32 | 20 | 6.94 / 6.87 / 6.81 |
| mps | fp16 | 20 | 5.14 / 4.42 / 4.44（logits 与 fp32 最大差 0.0028） |

MPS 的矩阵乘本身比 CPU 快 2.8 倍，但 568M 参数的交叉编码器在这块 GPU 上只有约 30% 利用率；MPS 与 CPU 打平说明这是算力上限而不是配置错误。正式运行里重排 p50 2.3 秒是因为多数问题经事实平面复核后不足 20 对、正文更短；20 对满载时就是 6.5 秒。查询嵌入 0.04 秒（mps）。

## 5. 结论与杠杆（供决策）

门禁在这台笔记本上**未达标，且原因不在并发模型或数据库**：一是 gpt-6-sol 两次调用的尾部（单次 p95 6.6 秒），二是本机 GPU 上的交叉编码重排（满载 6.5 秒，多进程并发时排队）。基线 5.11 / 5.12 的写法是「报告并发、数据集和硬件环境」，本记录给出了报告；是否算过门要看部署硬件。杠杆与代价如实列出（任何改动都要证明质量不降，基线 5.11 第 1 条）：

| 杠杆 | 预期效果（本机实测或推算） | 代价 / 需要的证明 |
| --- | --- | --- |
| 部署到服务器 GPU（T4 / A10 级） | 重排 6.5 秒 → 约 0.2–0.4 秒；并发 4 不再排队 | 部署对象；本记录的方法可直接复测 |
| 重排改 fp16 | 满载 6.5 → 4.4 秒（−32%） | 分数最大偏差 0.0028，排序是否变化要在冻结集上离线证明（无模型费用）；属于 `retrieval_version` 变更，走 M4 策略发布 |
| 重排输入 20 对 → 10 对 | 约减半 | 召回可能下降，需离线证明；同上走 M4 |
| 更小的重排模型（如 bge-reranker-base，278M） | 约 2 倍 | 质量需离线证明；同上 |
| 多条陈述的判定调用并行 | 只在 > 1 条陈述时省 2–4 秒（平均每请求 0.9 次判定，收益有限） | 纯工程改动，不改判定结果；需处理钉住线程之外的线程数 |
| 嵌入与重排分开的钉住线程 | 并发时事实平面从 4.2 秒回到 0.2 秒（p50） | 两条长期线程驱动 MPS 有重现记录 54 §3.0 卡死的风险，要先做进程级验证 |
| 回答模型换更快档位 | 单次 p95 6.6 秒的尾部才是并发 1 的大头 | 策略变更，M4 候选评测（三次运行 + 配对 bootstrap） |

**建议**：M3-11 记为「部分（已按要求测量，本机未达标）」；不为过门在 M3 内改检索或模型（那是 M4 的策略候选，且缺质量证明）；把「fp16 重排」「判定并行」作为 M4 的前两个候选登记，门禁在部署硬件上复测。可否决。

## 6. 发现与修复

### 6.1 停机时最后几秒的 span 会丢（已修）

冒烟里两个请求的尾部 span（answer 节点、第二个请求的 retrieve）没有到达接收器。原因：uvicorn 0.53 在优雅停机后重新抛出捕获的 SIGTERM（记录 67 的退出码 143），进程死于信号，Python 的 `atexit` 不运行，`BatchSpanProcessor` 里未满 5 秒的批次丢失。修复：`create_app` 增加 lifespan，停机时 `telemetry.flush()`；worker 与 MCP 入口在返回前显式 `telemetry.shutdown()`。回归测试 `tests/unit/core/test_telemetry.py::test_app_shutdown_flushes_spans_still_held_by_the_batch_processor`（批处理导出器 + TestClient 生命周期）。正式运行 137 个 trace 的 span 全部到齐（1,496 个，0 个导出错误）。

### 6.2 第一级被 Wi-Fi 断开与合盖睡眠污染（重跑）

首次 c1-cold 在 04:13–04:18 UTC 出现 14 个 `system_failure`：answer 节点先是 60 秒超时（`dependency_timeout`），随后连续 13 个 0 秒的 `ModelUnavailable`（三次重试全部即时失败），之后 04:18–04:59 UTC 没有任何 trace。`pmset -g log` 显示 14:19 本地时间合盖睡眠、14:48 DarkWake、14:59 开盖唤醒，睡前 Wi-Fi 先断。两点如实记录：

- 服务侧行为正确：网络丢失期间没有一条回答被产出，14 个请求都是空 `answer` 的升级，trace 与升级记录齐全；唤醒后同一进程无需重启即恢复（04:48 的请求第一次尝试超时、第二次成功）。这等于提前做了一次真实的「供应商中断」演练（M3-13 的用例之一）。
- 测量侧：`time.perf_counter()` 在 macOS 睡眠期间不走，级别计时看起来正常而墙钟差了 41 分钟。工具已改为同时记录墙钟并标记 `suspended_s`；第一级在新进程里重跑（§3.1 第二行）。后续长时间运行用 `caffeinate -i -s` 启动，并请决策人在运行期间保持开盖或接电。决策人 2026-09-25 同意此做法；§5 的门禁处置建议同日获批（见 §5 末）。

### 6.3 观测缺口（登记，未修）

- 升级记录的 detail 只有「answer: ModelUnavailable」，span 只有 `dependency_unavailable`；具体是 429、连接错误还是 5xx 从审计里看不出来。建议把异常类名（不含消息）写进 span 属性。
- `/v1/ask` 没有每请求的访问日志行；节点失败不在 WARNING 级日志出现。排障目前只能靠 Trace。
