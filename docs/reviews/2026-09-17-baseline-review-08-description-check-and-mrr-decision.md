## 3. MRR 不设的理由（备查）

- 事实回查后的 top 5 全部进入模型上下文，首条 gold 在第 1 位还是第 3 位对答案质量影响很小；MRR 适合单结果展示场景。
- 排序质量主要取决于 Reranker，DEC-002 未选型；在此之前写死 0.80 属于基线第 10 节反对的"凭偏好锁定"。
- 若设为门禁：项目无实测基线，0.80 可达性未知，会单独增加最终验收失败的风险；标注需补等价 gold 集合，否则等价条款排第 1 会被误判为 miss；5.8 的"非目标下降不超过 1pp"对每查询在 1/0.5/0.33 之间跳变的指标噪声过大；并会诱发把证据裁到 top 1～3 的错误优化。
- 若只"另报"：成本小且对 DEC-002 选 Reranker 有判别价值，但决策人选择暂不引入，避免对外描述出现无阈值指标。后续如需，只需在 5.9 与 M1-21 各加一句，不影响其他条款。

## 4. 建议的修订稿措辞（供决策人取用，基线不因此改动）

> 技术栈：Python、FastAPI、LangGraph、PostgreSQL/pgvector（词法检索 + 向量检索）、RRF、Reranker、Redis、Langfuse、OpenTelemetry、MCP、Docker（开发中，以下指标均为目标值）
>
> - Agent Harness 与医学安全：基于 LangGraph 构建 Intent → Retrieve → Evidence Verify → Safety Check → Answer/Escalate 状态机，使用 Schema、Skill Registry、权限控制、超时降级和 Trace 重放约束执行；封装不良事件线索提取、超说明书用药检查及方案偏离核验等 Skills，不提供诊断与处方建议。基于不少于 150 条安全样本验收，目标正确拒答率≥95%、越权拦截率≥98%、高风险问题升级召回率≥95%。
> - 可信知识治理与混合检索：使用 PostgreSQL 维护 300–500 份药品说明书、临床方案、SOP 及医学指南的 `draft/active/archived` 版本链、生效时间、来源哈希和页码；采用词法检索 + pgvector + RRF + Reranker 召回并回查有效原文。基于不少于 300 条证据标注问题验收，目标 Recall@5≥85%、引用准确率≥95%、失效版本引用率为 0%。
> - 受控自进化 Loop：实现 Execute → Observe → Reflect → Adapt → Approve → Deploy 闭环，将用户反馈和 Verifier 结果归因为检索、意图、生成、知识缺口或安全问题，生成 Prompt、Rule、Skill 及检索参数候选；每轮使用不少于 200 条历史 Trace 回放，发布门槛为目标任务成功率提升≥5 个百分点、非目标能力下降≤1 个百分点且安全指标不下降；候选须经人工审批后灰度发布，支持一键回滚，不在线直接修改生产策略。
> - 评测、可观测性与服务集成：使用 Langfuse 和 OpenTelemetry 记录检索证据、节点决策、工具调用、延迟、Token 及成本；通过 FastAPI 提供接口，并将只读医学检索能力封装为携带身份权限的 MCP Server。目标普通问答 P95≤8 秒、复杂工作流 P95≤15 秒，同等质量下单次 Token 消耗降低≥25%。
