# 实现记录 166：本地模型 lane 的有界背压与卡死快速拒绝

日期：2026-10-09。范围：PERF-01B 的零模型工程切片。本轮没有调用外部模型 API，费用为 0；没有运行真实 API 容量测试，因此不产生新的 P50、P95、吞吐或质量结论。

## 1. 问题与历史证据

生产运行时把 bge-m3 查询嵌入与 bge-reranker-v2-m3 重排固定到同一条 `PinnedThread`。这是记录 54 的稳定性约束：Metal/MPS 曾被多个短生命周期线程驱动并卡死，单一长期线程让超时后可由 supervisor 重启进程。

该线程此前使用无上限 `queue.Queue`。API 并发超过本地模型吞吐时，任务仍会全部进入队列；调用方只能等到 60/120 秒模型调用时限才失败。记录 111 在并发 16 时测得 24/30 失败，P50 60.7 秒、P95 61.0 秒。失败均安全地升级为 `system_failure`，但排队没有上限，故障反馈太慢，也会继续占用内存与请求线程。

## 2. 实现

`PinnedThread` 保留单 worker 和原有模型/排序行为，只约束准入：

- 默认总容量 8，包含正在执行与等待中的调用；
- 新调用最多等待 250 ms 获取容量；仍饱和时返回可重试 `dependency_timeout`；
- 已接纳调用仍使用原有 120 秒默认执行等待；真正超时仍是不可重试 `dependency_timeout`，并把 lane 标为 `stalled`；
- `stalled` 后的后续调用立即返回可重试 `dependency_unavailable`，由 supervisor 重启，不再每个请求重复等待长超时；
- worker 在成功、模型异常和调用方已经超时后都会于实际任务结束时归还槽位；卡死任务不会虚假归还容量。

8 个总在途沿用记录 111 的单机拐点证据，是当前部署的保守保护值。它限制任务而非请求：一次请求可能先做嵌入、再做重排，所以它只保证模型 lane 不会无限堆积，不宣称提供请求级公平性。

## 3. 为什么本轮不拆线程或扩大 batch

词法与向量通道共享一个身份绑定的 PostgreSQL 事务。把它们直接交给不同线程会同时驱动同一 psycopg 连接；改成不同连接还要定义身份、`as_of` 和事实快照的一致性。因此没有用线程池包装现有函数。

嵌入与重排也没有拆成两条 MPS 线程，因为记录 54 的原始故障正来自多线程驱动 Metal。记录 77 的真实 chunk 微基准里，MPS batch 8 与 20 的满载重排约 6.5–7.0 秒，几乎没有改善；记录 113 的逐句重排测试中 batch 大于 8 反而受 padding 影响变慢。现有证据不支持把“增大 batch”当成免费优化。

跨请求动态 batching、ONNX/CoreML 或独立重排服务仍可能有价值，但要在独立进程内测吞吐、尾延迟、排序一致性和故障隔离，不能由现有 batch 参数结果直接推出。

## 4. 测试与自审核

- 新增确定性测试：容量 1 时，一个运行任务占满总容量，第二个调用在 10 ms 准入等待后以可重试 `dependency_timeout` 失败；释放后第一个调用正常完成。
- 扩展卡死测试：首个调用超时并设置 `stalled`；第二个调用立即得到可重试 `dependency_unavailable`。
- 相关运行时、readiness 与 MCP 测试共 18/18 通过。
- 全量干净环境 `env -u DEBUG make check`：**1721 passed、70 skipped、1 个既有短 HMAC key warning**；Ruff、442 个文件格式、mypy 189 个 source file、评测输入审计与 Schema 漂移均通过。

第一次直接运行 `make check` 时出现 8 个配置测试失败，错误均为 `Settings.debug: Input should be a valid boolean`。检查发现执行环境注入了 `DEBUG='release'`；它不是 `.env` 内容，也与本轮 diff 无关。清除该外部变量后全量通过。失败没有被改代码或跳过测试掩盖。
