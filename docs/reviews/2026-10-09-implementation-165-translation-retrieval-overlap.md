# 实现记录 165：查询翻译与原始检索重叠、有界并发和过载失败关闭

日期：2026-10-09。范围：PERF-01A 的零模型工程切片。本轮没有调用模型 API，费用为 0；没有重跑真实 API 性能，因此不产生新的 P50/P95 或容量结论。

## 1. 为什么先改这一段

记录 111 的真实语料容量运行显示：检索节点中位约 6.4 秒，超过作答节点约 4.1 秒；并发 4 到 8 出现拐点，并发 16 时 24/30 请求超时。已发布检索会先调用远程查询翻译，再依次执行原始/改写查询的本地词法与向量检索，二者此前完全串行。

查询翻译使用独立的模型网关和费用账本短连接；原始检索使用请求的身份事务、PostgreSQL 和本地 pinned 模型线程。两路没有数据依赖，翻译结果只在完成后追加为一个搜索 query，因此可以重叠等待而不改变 RRF、事实回查或重排规则。

## 2. 实现

`TranslationPool` 是进程级有界执行器：

- 4 个 worker，与历史单机并发拐点的稳定侧一致；
- 总容量 8，包含执行中与排队任务，即最多 4 个运行、4 个等待；
- 第 9 个调用最多等待 250 ms 获取槽位；仍饱和则抛出可重试 `dependency_timeout`；
- 不使用 caller-runs，也不在过载时静默跳过翻译；
- `ContextVars` 随任务复制，`retrieval.translate` 与 `llm.call` span 仍属于原请求 Trace；
- 缓存命中、指定来源缺失以及未启用翻译的路径不会提交任务。

检索顺序变为：提交翻译 → 执行原始/改写查询与文档聚焦 → 等待翻译 → 若得到新的英文 query，再执行该 query → 沿用原 RRF、事实回查和重排。正常路径的 query 集合和融合顺序保持原样；这里只调整两个独立等待段的时间重叠。因此不修改 retrieval version。过载行为属于运行故障契约，会进入系统失败/重试路径，不冒充“无证据”或以缺少翻译的答案继续。

## 3. 自审核中否决的第一版

第一版在容量满时采用 caller-runs：队列有界，但请求线程会直接执行翻译。若 16 个请求同时进入，4 个池线程之外仍可能有多个请求线程并发调用模型，实际并发没有被限制。这与“有界并发”目标冲突，定向测试通过也不能证明设计正确。

修复后改为 250 ms 有界等待，超时即失败关闭。测试明确证明饱和时翻译函数调用数为 0、检索调用数为 0，错误为可重试 `dependency_timeout`。

## 4. 为什么没有直接并行词法与向量

词法、向量与事实回查当前共享同一个身份绑定的 PostgreSQL 事务。psycopg 连接不应被两个执行线程同时驱动；为了并行而临时开第二个连接，还要证明同一身份、同一 as-of 和足够一致的事实快照。向量嵌入与重排又共用为规避 MPS 卡死而建立的单一 pinned 模型线程，表面并发可能只把等待移到另一层队列。

因此本切片只重叠真正独立的远程翻译与原始检索。词法/向量并行、重排批处理或独立服务归入 PERF-01B，先设计事务一致性、模型队列与资源预算，再实现。

## 5. 验证

- 3 个新增确定性测试：容量与 Trace context 传播；翻译先启动且最后仍加入融合；饱和时搜索前失败关闭。
- 相关检索/缓存/翻译测试：13/13 通过。
- 全量 `make check`：**1720 passed、70 skipped、1 个既有短测试 HMAC warning**；Ruff、442 个文件格式、mypy 189 个 source file、评测审计与 Schema 漂移均通过。
- 评测审计四项既有 warning 不变；模型调用 0，新增费用 0。
