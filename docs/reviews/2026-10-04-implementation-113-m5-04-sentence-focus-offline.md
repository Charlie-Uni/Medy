# 实现记录 113：M5-04 第二个成本候选——作答上下文布局（短别名 + 逐句聚焦），只做零费用部分

日期：2026-10-02 至 2026-10-04。决策人处置（记录 112 §1 第 3 项）：M5-04 选逐句裁剪；先开发并做不产生 API 费用的检查，付费评测等账单核实后再安排；单独的模型路由达不到现行 token 降幅目标。本记录全部工作没有调用付费接口，费用 0。

## 1. 先弄清 token 花在哪里

在真实语料的全量运行 F2（`2026-10-02-full-ask-v4-released`，614 题）上，用存档的证据分块重建作答提示词，以代理分词器（tiktoken o200k_base；gpt-6 的分词器不公开）计数：

| 部分 | 每题 token | 占全部模型调用 token（3,213）的比例 |
| --- | ---: | ---: |
| 作答提示词合计 | 2,230 | 69% |
| 　其中证据正文（8 段） | 1,316 | 41% |
| 　其中每段的头尾标记（两个 UUID） | 584 | 18% |
| 　其中系统提示 | 168 | 5% |
| 其余（翻译一次、作答输出、判定调用） | 约 980 | 31% |

两个结论决定了设计：每段证据的 UUID 标记占了近五分之一的 token，去掉它们不丢任何信息；证据正文只占 41%，所以 25% 的总降幅意味着正文要删掉三分之一以上——这也解释了记录 108 为什么按段裁剪（删 3/8 段）只换来 25.7%。

## 2. 实现：可发布参数 `evidence_focus`

`retrieval_params/hybrid` 下新增键 `evidence_focus`（`src/medops/harness/evidence_focus.py`，接线在作答节点、API 运行时与三个评测运行器）：

| 取值 | 做法 | 不变的部分 |
| --- | --- | --- |
| `off`（默认） | 现有布局，提示词逐字节相同（测试锁定） | — |
| `compact-v1` | 头尾标记里的 chunk / 文档 UUID 换成 `E1` / `D1` 这样的别名；模型按别名引用，作答节点映射回 chunk id；臆造的别名与臆造的 chunk id 同样过不了 grounding 检查 | 证据正文、状态、校验、引用 |
| `sentfocus-v1` | 在 compact 之上，把每段拆成句子单元，用已加载的本机重排模型（bge-reranker-v2-m3）对问题打分；每段至少留最高分的一句，其余句子在全部证据范围内按分数竞争，直到保留 60% 的证据 token；删掉的地方标 `[…]` | `AgentState.evidence` 仍是完整分块（哈希校验，基线 3.3），注入筛查在完整正文上已做，Verifier 对完整分块判定，引用仍按分块 |
| `sentfocus-v2` | v1 加三条保护：单元得分取「问题」与「最丰富的改写查询」两者的最大值（词表改写带英文词汇，缓解中文问题对英文证据）；每段保留最佳句的前后相邻句；重排第 1 段整段保留 | 同上 |
| `sentfocus-v3` | v2 去掉「第 1 段整段保留」 | 同上 |

该键只改变模型读到的内容，不改变检索，所以进入 `model_config_version`（后缀 `;ctx=`），不进入检索版本与缓存键。参数常量在模块里固定，`focus_check.py` 只读取、不扫参。回放运行器现在在任何付费行之前打印两臂的生效配置（记录 107 的教训落成代码）。测试：`tests/unit/harness/test_evidence_focus.py`（11 个）、策略加载器与回放臂设置各 1 个。

## 3. 零费用检查工具与三个版本的实测

`evals/harness/tools/focus_check.py`：对存档运行的每一题，从库里重读证据分块，按作答节点的方式渲染各布局，报告（a）各布局的提示词 token 与占全部模型 token 的降幅；（b）本机打分耗时；（c）保留率——标注的 gold 关键句在聚焦后是否仍可见、每条存档陈述所依赖的句子（重排模型对陈述打分最高的单元）是否仍可见。参数在测量前已提交（f122f11、ac358e6、fb9dc0a），每个版本测一次。

| 版本 | 作答提示词 token / 题 | 占全部模型 token 的降幅（输入侧） | 保留证据 token | gold 关键句保留 | 陈述依赖句保留 | 存档成功题中 gold 句被隐藏 | 本机打分 p50 / P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 2,230 | — | 100% | — | — | — | — |
| compact-v1 | 1,874 | 11.1% | 100% | 100% | 100% | 0 / 458 | 0 |
| sentfocus-v1 | 1,390 | **26.2%** | 61.9% | 93.95%（466/496） | 88.5%（913/1032） | **26 / 458** | 1.1 s / 2.8 s |
| sentfocus-v2 | 1,491 | **23.0%** | 71.4% | **99.6%**（494/496） | 95.3%（983/1032） | 2 / 458 | 1.9 s / 4.1 s |
| sentfocus-v3 | 1,476 | 23.5% | 70.0% | 97.6%（484/496） | 90.7%（936/1032） | 12 / 458 | 2.1 s / 4.5 s |

运行目录：`evals/harness/runs/2026-10-02-focus-check-v1`（v1）、`2026-10-04-focus-check-v2`（v1 + v2 同一遍）、`2026-10-04-focus-check-v3`。输出侧的节省（引用写 `E1` 而不是 UUID，约每题 20–40 token，约 1%）未计入。

### 3.1 v1：降幅过线，但会藏掉答案

26.2% 刚过 25%，但 458 道存档成功题里有 26 道（5.7%）的 gold 关键句被裁掉。30 条被隐藏的关键句全部在英文或中英混合的题上（中文题 100% 保留）：11 条是单句本身对问题打分偏低（中文问题对英文句子，跨语言打分弱），19 条是答案跨两句、其中一句被裁。记录 108 已经证明，零费用的直接损失估计还会低估真实损失（模型还依赖旁证句）。按这个数字，付费试跑大概率重蹈 rerank5 的结局（−3.5 pp）。实现方不建议以 v1 试跑。

### 3.2 v2：答案几乎都在，但降幅不够

三条保护把 gold 保留率提到 99.6%（按重排名次：第 1 段 386/386、第 2–8 段 108/110），陈述依赖句 95.3%。代价是只删掉 28.6% 的证据正文——相邻句规则在平均 4 句的分块里留下 3 句，预算（60%）已经不起作用——输入侧降幅 23.0%，低于 25%。加上未计入的输出侧约 1%，仍在门槛边上。打分耗时翻倍（两套查询变体）。

### 3.3 v3：去掉整段保留，没有换来降幅

去掉「第 1 段整段保留」只把降幅从 23.0% 提到 23.5%——相邻句规则本来就把第 1 段的大部分留下了——却把 gold 保留率从 99.6% 拉回 97.6%（第 1 段 376/386），被隐藏的成功题从 2 道变成 12 道。v3 被 v2 完全压制，不再考虑。三个版本放在一起看：相邻句规则是保留率的来源，也是 token 的去处；在这组规则下，「≥ 25%（代理计数）且 gold 保留 ≥ 99%」两者同时满足的点不存在。能过线的只有 v1，而 v1 会藏答案。

### 3.4 打分耗时

真实语料上每题平均 33 个句子单元，bge-reranker-v2-m3 在 M3 的 MPS 上约 25–35 ms 一对，v1 每题 p50 1.1 s、v2 1.9 s。批次大小 2 / 4 / 8 / 16 / 32 / 64 都试过，8 以上反而更慢（MPS 上 padding 的开销），按长度排序分批也没有帮助。这笔时延会直接加在普通问答上，而 P95 本来就未达标（13.8–15.2 s 对 8 s，记录 111）。真正的出路是重排模型离开 Python 推理（ONNX / CoreML）或独立服务，那是另一项工程。

## 4. 没有做、以及为什么

- **没有付费试跑**：决策人要求核账前暂停。候选文件已备好并对照已发布策略校验通过（重述四个已发布键）：`evals/replay/candidates/2026-10-02-sentence-focus-on-bundle.json`（取值待按 §5 决定）、`2026-10-02-compact-headers-on-bundle.json`（无损部分单独归因用）。一轮试跑约 4 USD，三轮约 13 USD。
- **没有改判定器**：判定调用的提示里也带 chunk UUID（每条被引分块约 20 token），改它能再省约 1%，但 Verifier 版本受 ADR-0011 管辖，不在本候选范围内。
- **没有把译文作为打分变体**：`rewritten_queries` 上限 3 条（基线 5.2），译文不在其中；v2 用词表改写代替。
- **关于 INV-EVAL-01**：保留率用到了主集的 gold 标注，与记录 93–95 用 recall_diag 迭代检索候选的做法同类——按聚合诊断调整规则，不按题调参；三个版本的规则都是先写进代码再测，每个版本只测一次，测过的版本不改。最终的质量结论只能来自回放门禁。

## 5. 留给决策人

1. **选哪个版本试跑**（核账之后）。实现方的看法：v1 不值得花钱（会藏掉约 6% 的答案句）；v3 被 v2 压制；**只有 v2 值得跑一轮**（约 4 USD）：它在质量上最稳，降幅在代理计数下是 23.0% 加未计入的输出侧约 1%，过不过 25% 只有提供方的真实计数能回答——rerank5 那次真实降幅比代理估计高出约四分之一，但那是另一种删法，不能照搬。若真实计数仍不到 25%，作答提示词这条路就到头了：剩下的杠杆是判定器提示（约 1%）和模型路由（按费用而非 token 计），后者需要修订门禁口径。候选文件 `2026-10-02-sentence-focus-on-bundle.json` 已改为 `sentfocus-v2`。
2. **接受时延代价吗**：逐句聚焦每题多 1–2 s 本机耗时，P95 会更差。若 P95 比 token 更重要，`compact-v1` 是零时延、零风险的 11% 无损节省，可以单独发布，但达不到 M5-04 的 25%。
3. M5-04 的里程碑状态：实现方保留为「待做」——候选已实现并通过离线检查，但验收标准（同质量下 token −25%）尚无实测；若决策人认为「候选就位」应记为「部分」，进度从 80.4% 变为 81.0%。
