# 实现记录 167：通道并行收益评估与向量候选漂移

日期：2026-10-09，收尾核验：2026-10-10。对应 PERF-01C；承接记录 165/166。Hosted LLM 调用 0，API 费用 0。

## 1. 范围、固定条件与结果

使用实际生产部门隔离 BM25、本地 BGE-M3/MPS、普通 MA 角色和 `medops_v2`。固定 8 道法规/药品问题、K=20、10 轮，两臂相邻且交替执行。顺序臂先词法后向量；并行臂使用两个预先打开并绑定同一部门身份的连接，词法在一个 worker 上执行。每臂 80 次。

此实验只测检索通道，未包含翻译、文档聚焦、融合、重排、生成、核验或 API 排队。预开连接省去了第二个连接的建立成本，测量条件比实际请求路径有利。没有把这套双连接装配接入生产，也没有解决两连接共享事实快照的问题。

原始汇总：[benchmark JSON](2026-10-09-implementation-167-channel-overlap-benchmark.json)。固定的旧生产组合版本为 `19c755df9adf44e8df9badba547f9b0f21391edbf8f3ab3631f5ea0256b3e4d1`。

| 指标 | 顺序 | 并行 |
| --- | ---: | ---: |
| 中位耗时 | 128.95 ms | 122.22 ms |
| P95 | 147.85 ms | 141.20 ms |
| 词法中位耗时 | 6.57 ms | 6.70 ms |
| 向量中位耗时 | 122.42 ms | 122.07 ms |

中位收益仅 6.73 ms（通道时间的 5.2%），相对记录 111 的 9.5 s 完整问答中位数约 0.071%。收益不足以支持增加连接、事务和一致性设计。PERF-01C 的词法/向量并行评估完成，当前决定为不实施。重排服务与动态批处理拆为 PERF-01D，仍需独立证据。

## 2. 发现的错误与排除过程

最初基准把候选逐项一致作为断言，实际遇到：

```text
RuntimeError: vector rankings changed for query 5 in sequential arm
```

这发生在顺序臂，不能归因于并行线程。改为统计重复结果后：词法两臂各 76 次比较均无顺序/集合变化；向量顺序臂有 37 次集合变化、并行臂 36 次，最小 Top-20 交集只有 12。

定位顺序：

1. 同一 query 的 12 次 MPS 嵌入只有 1 个哈希，最大绝对差 0、余弦 1.0。当前样本未发现 embedding 非确定性。
2. 固定向量重复 20 次仍出现 2 种排名、10/19 次集合变化，最小交集 19/20。问题在数据库检索侧。
3. 显式比较定制计划与通用计划：8 道题中 6 道的集合不同；`relaxed_order` 下最小交集 12/20。改成 `strict_order` 仍有 6/8 不同，不能解决计划切换。
4. 把 `ef_search` 从 40 提到 1000 仍存在相对精确扫描的缺口，不能仅靠加大 HNSW 搜索宽度解决。
5. 一组固定计划诊断中，定制计划对精确 Top-20 的交集为 `[15,12,20,18,19,18,19,20]`，通用计划为 8/8 的 20/20。两种固定计划自身重复稳定。此处只证明当前 8 题、当前语料与统计下的现象，不能推广为通用计划始终精确。

psycopg 会在同连接重复执行达到阈值后预备语句；PostgreSQL 的自动模式又会比较定制和通用计划的估计成本。相同向量语句的两个计划产生不同候选，因而连接复用与查询次序影响结果。记录 168 进一步以实际缓存语句的 `EXPLAIN EXECUTE` 确认：当前诊断中的 custom 使用 HNSW，generic 使用排序扫描，不能把两个计划都称为近似 HNSW 扫描。机制依据：[psycopg 预备语句文档](https://www.psycopg.org/psycopg3/docs/advanced/prepare.html)、[PostgreSQL 17 PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html)。记录 42 的可复现证据来自当时 16 份文档、2,662 chunk 的较小语料；当时默认计划使用精确排序，其结论不能直接覆盖目前 333 份 active 文档。

## 3. 环境事故与恢复

本轮 Git 操作曾卡在 iCloud `dataless` 文件：分支 ref 与 40 个 loose object 只剩占位。根据已推送的准确 HEAD 恢复本地分支 ref，并重新抓取远端对象；删除了一个不可读取的 Codex 临时 turn-diff ref，项目分支与远端分支未改变。随后 `git fsck --connectivity-only --no-dangling` 通过，objects 中占位数量归零。

虚拟环境也出现约 8,072 个占位文件。先用 `brctl download` 补下载，并按已有锁版本重装卡住的 redis、pydantic-core、tokenizers、zstandard，曾恢复至占位 0；但 2026-10-10 自审又出现 5,064 个占位，pytest 导入 langsmith 时等待文件落地。临时补下载未消除环境根因。后续将可执行环境迁到 iCloud 范围之外，处理和复验记录在 168。

项目 Makefile 早期已记录 Documents/iCloud 对隐藏 `.pth` 的影响；这次是另一种文件可用性问题。上述恢复不构成新的模型质量或性能成绩。
