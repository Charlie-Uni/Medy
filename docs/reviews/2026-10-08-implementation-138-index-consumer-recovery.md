# 记录 138：增量索引消费者与真实积压恢复

日期：2026-10-08。阶段 2 / OPT-15。本轮自审通过；长期部署和缓存运行证据仍待完成。阶段 1 的模型预算仍未收到决定，没有付费复核调用。

## 为什么继续补

记录 137 能检测缺索引，但生产向量索引此前依赖手动全库构建。只检测不恢复无法避免新一轮“入库后检索不到”。本轮让发布事件分别驱动词法、向量与缓存处理，并保留每个消费者的独立确认。

## 具体实现

1. `retrieval.maintenance` 为每批 1–100 条事件提供逐事件 savepoint：成功的索引写入与 ACK 同事务，失败的局部写入回滚，失败事件保留 pending。既有 outbox `attempts/last_error` 只保存消费者和异常类型，不保存异常原文、SQL、密码或正文。
2. `worker.retrieval` 提供三个显式消费者、必填目标库名、单批运行和持续轮询。默认批次 10、空闲/失败间隔 2 秒；SIGTERM 等当前批次完成。缓存入口拒绝 off/memory，防止把另一个进程的内存缓存失效当作共享失效。
3. 向量构建增加 `doc_ids` 范围，None 保留原全库构建语义，空列表不嵌入任何文本；outbox 每次只处理当前文档缺失的块。元数据版本不符或缺失时保持未确认，要求显式构建。
4. 处理事件时锁定并读取当前文档状态，不按旧事件盲目回放状态。active/archived 保留可检索索引，draft/withdrawn 移除派生索引；归档文档仍须满足显式历史查询与日期条件，普通查询不因此读到归档数据。
5. `vector-index` 使用独立 ACK，监测和指标增加这一消费者。早期 `published_at` 不充当处理依据。

没有修改文档发布规则。现有状态机只允许 **draft → withdrawn**，active 的退出路径是归档。本轮测试最初假设 active 可直接 withdrawn，被真实数据库以 `CheckViolation: illegal status transition active -> withdrawn` 拒绝；已按项目状态机修正，并补查 ACL 生产者允许 draft ACL 事件的情况。

## 剩余边界

- 尚未启用长期服务或 compose profile；本机一次恢复不保证将来新增事件有人持续消费。共享 Redis 的持续失效在阶段 6 联合验证。
- 每条事件失败可继续本批其他已领取事件；如果足够多的坏事件占满最前一批，后续事件仍会受阻。保留 pending 和告警，需修复明确问题，没有自动丢弃/死信通过。
- 本地 embedding 没有硬推理时限，GPU 卡死需进程监督；本轮批次和 SQL 有界不等于整次本地推理有硬时间保证。
- `attempts/last_error` 是既有事件级诊断，最新消费者错误可能覆盖上一消费者的错误类型；各消费者 ACK 与 pending 独立。
- 索引覆盖检查不会证明每个向量的语义正确；生产规格核对、来源哈希与检索质量评测各自负责不同证据。
- 更严格的正式评测预检与运行身份绑定继续下一轮。
