# 实现记录 169：重排合批与独立进程的本地评估

日期：2026-10-10。任务：PERF-01D。只使用已许可的本地语料和本地固定模型，hosted 模型调用 0，API 费用 0 USD。不改变生产模型、精度、检索版本、候选上限、排序规则、缓存或发布策略。

## 1. 为什么做这轮

记录 77/111 的真实 API 实验表明，并发时查询嵌入会排在重排后面，共享模型线程形成资源等待。记录 166 已补有界准入和卡死拒绝，但没有提高计算吞吐。记录 167/168 又表明，词法/向量双连接并行的乐观收益仅约 6 ms，不足以成为主要加速方向。

本轮检验两个具体问题：同部门的多个就绪请求能否共享重排预测批次；独立本地模型进程崩溃或超时后，调用者能否失败关闭并用新进程恢复。未先把模型拆成多个 MPS 线程，也未直接接入网络推理服务。

### 三个臂

| 臂 | 一次 `predict` 包含 | 低层 batch | 请求完成规则 |
| --- | --- | --- | --- |
| FIFO | 1 道题的 20 对文本 | 8 | 每题单独完成 |
| merge2 | 同部门 2 道题的 40 对文本 | 8 | 同组两题完成后一起返回 |
| merge4 | 同部门 4 道题的 80 对文本 | 8 | 同组四题完成后一起返回 |

`CrossEncoder.predict` 在锁定的 sentence-transformers 5.7.0 中已按长度排序并恢复输入次序，本轮沿用它；合并多个 query/document 对后，再按各题原来的候选数拆回。它不会把别题 query 配到当前题 document 上。[官方 CrossEncoder 文档](https://www.sbert.net/docs/package_reference/cross_encoder/model.html)说明其输入为成对文本，支持 batch、固定修订和截断长度；具体排序机制以本机锁定实现为准。

20 对文本、batch 8，FIFO 每题有 3 次底层预测批次；四题合计 12 次。merge2 和 merge4 各为 10 次，并非 merge4 比 merge2 又减少一半。跨题长度排序可能改变 padding 和浮点计算的组合，因此必须实测原始分数及排名，不能假设数学上的逐对独立就保证机器浮点结果完全相同。

每个部门的四题组成一个“同时就绪”的 backlog burst。先为每个部门/臂完整预热一次，FIFO 预热也生成参考分数；之后 3 轮、按轮次和部门轮换臂顺序，总计每臂 36 个请求、720 个文本对，三臂共 108 个请求、2160 对。候选并列仍按 `chunk_id` 排序，比较完整 20 名和 Top-8 的次序，而非只比较集合。

预登记进入下一步的条件：完整排名与 Top-8 均无变化、总体吞吐至少提升 20%、各部门 burst 完成时间 P95 不退步；满足后也只进入更大范围的排序与质量审计，不直接发布。

### 计时解释

完成时间是 worker 内从四题同时就绪到该题所在组完成的墙钟；不包含 HTTP、真实请求到达间隔、合批等待窗口、查询嵌入与远程模型调用。吞吐使用每个 burst 的父子进程往返时间，按请求数正确去重；同时保存 worker 时间与 IPC 差额。冷加载和预热从温态计时中排除并单独记录。

这是一种乐观的就绪队列微基准，尚未实现动态合批调度器。没有低流量 batch timer、取消、队列公平性、实际模型 lane 容量 8、嵌入/重排竞争或网络传输的完整模拟。因此本文的完成时间 P95 不是 API P95，也不能与记录 111 的完整回答时延直接相减。

父子进程平均 burst 往返减去 worker 计算为约 **0.89 / 0.85 / 1.10 ms**。这只证明该本地 Pipe 原型的消息开销较小，未比较真实进程内 API 路径和生产网络服务，不能单独推断服务化后的整体收益。

## 4. 独立进程与故障边界

模型只在 `multiprocessing` 的 `spawn` 子进程内加载，通过一条长期 pinned 线程调用 MPS，父进程不初始化该模型。选择 spawn 避免复制已经初始化的 Metal 状态；[Python 3.11 multiprocessing 文档](https://docs.python.org/3.11/library/multiprocessing.html)描述了独立解释器启动和可序列化入口要求。

原型只有一个在途 IPC 调用，使用本地私有 Pipe；不开放网络端口。捕获端先做普通角色事实回查，评分端不接收数据库 DSN；同一个 burst 不能混部门。输入超过 20 候选、重复请求/候选、文本哈希不符、分数数量不符或非有限数值会被拒绝。

故障演练分别向已加载模型的子进程注入进程退出和阻塞等待。父进程遇 EOF/截止时间时终止并回收子进程、丢弃旧 Pipe、返回错误，不产出替代分数；重新 spawn 后，用同一真实题验证恢复排名。阻塞等待是可控注入，**没有重现历史 Metal 驱动卡死**，不能据此保证所有 GPU 驱动故障都能靠杀进程恢复。

| 注入 | 检测并清理 | 父进程继续 / 子进程停止 | 新进程真实题恢复排名 |
| --- | ---: | --- | --- |
| `os._exit(86)` | 55.37 ms | 是 / 是 | 与原参考完全一致 |
| 阻塞等待，调用截止 250 ms | 311.56 ms | 是 / 是 | 与原参考完全一致 |

故障分支的错误契约为 `RuntimeError: worker unavailable; request failed closed`，代码与定向测试核对；预期注入由运行器捕获并记录 flags，不是未处理异常堆栈。真实模型加载到子进程 `ready` 的三次耗时为 **7.25 / 8.60 / 7.54 s**，其中不含题目预热/首次推理，不把它写成 API 冷启动。

**进程原型验证通过，生产独立服务仍属选做。** 本批对退出/阻塞的隔离和恢复有效；要实际拆开嵌入/重排，还需两个 MPS 进程共同运行时的资源与故障检查、请求身份/结果绑定、队列与取消、Trace/readiness 和正式质量/容量验证。未获得计算收益前继续使用现有运行结构，未来明确部署资源后再评估。

## 7. 技术名词与取舍

| 名词 | 在本轮中的含义 | 容易混淆的地方 |
| --- | --- | --- |
| FIFO | 按题逐个执行，先进入的题先完成 | 每题内部仍是 batch 8，并不是每个文本对都单独 forward |
| 动态 batching | 在有界等待窗口内聚合多个已到达请求再推理 | 本轮只测“已同时就绪”的合批上界，未实现到达调度和等待窗口 |
| padding | 将一个底层 batch 的序列补到共同长度 | 减少 batch 数也可能增加补齐的 token，不能用 batch 数直接算速度 |
| cross-encoder | 将 query 和一个候选正文共同送入模型，输出相关性分数 | 不能像双编码器向量那样预先算好单个 document 的最终相关性 |
| IPC / Pipe | 同机两个进程之间的私有消息传递 | 往返开销、故障隔离与网络服务能力是不同的验证对象 |
| spawn | 用新解释器启动模型子进程 | 需要可导入入口与可序列化参数；不能将含 Metal 状态的已初始化线程直接复制过去 |
| burst 完成 P95 | 同部门四题同时就绪时，所有逐题完成时间样本的第 95 百分位 | 36 个样本来自 12 道重复题，不是 36 个独立业务题，也不是 API 端到端 P95 |

保留同一模型、fp32、batch 8 和 pinned 线程，是为了只改变跨请求分组，避免同时混入精度、推理引擎和模型质量变化。模型独立进程原型用于验证退出/恢复边界；它不会增加同一块 M3 GPU 的算力，还会带来模型冷加载、内存和部署管理成本。

ONNX/CoreML、实际 token 长度分桶、fp16、服务器 GPU 都可作为后续单变量候选，但本轮没有验证它们的质量或性能。采用新引擎、精度或分组策略前仍需分数/排序与证据覆盖对照；需要更换部署资源时先明确部署条件，再测完整容量。
