## 4. OPT-07 BM25

### 4.1 目标与价值

BM25 是关键词相关性排序方法，综合词频、逆文档频率和文档长度归一化。药品名称、方案编号、指南代码等精确线索适合用它检索。当前 A2 的排序在语料扩大后受高频词干扰；本项目已有同条件实验支持 BM25 的价值。

所有者于 2026-10-09 明确决定切换 BM25。生产现在使用部门隔离版 D，并继续与既有向量通道融合。这个决定基于词法召回、时延和项目展示价值的综合判断；它不改写修订 5 按预登记 `+5 pp` 规则得出的“D 未胜出”历史结论。

### 4.2 已做的实验

| 指标 | A2 | D | 条件与解释 |
| --- | ---: | ---: | --- |
| Lexical Recall@20 | 49.3% | 78.7% | 75 条语言一致探针；约 +29.4 pp；均低于原 90% 词法目标 |
| 词法 P95 | 164 ms | 40 ms | 同组历史实验条件 |
| 主集检索 Recall@5 | 85.71% | 87.34% | 553 条有 gold；两侧翻译关闭；只换词法通道 |
| 配对差 | — | +1.63 pp，CI [+0.18,+3.26] | 低于原 +5 pp 替换规则 |

这里“端到端”指融合、文档聚焦和重排后的检索结果，不包含生成回答。+1.63 pp 不能直接当作回答正确率提升，也不能与开启翻译的 87.16% 混成同一对照。

D 最初使用独立 PG17 实验环境并通过 22 项适配器测试；2026-10-09 的生产实现把语料按 ACL 复制到 MA/PV/CO 三个独立 BM25 索引，迁移和生产测试扩展到 migration 0022。依据：[ADR-0002 修订 5/6](adr/ADR-0002-lexical-retrieval-selection.md)、记录 124、记录 162。

### 4.3 技术选项

| 选项 | 价值 | 代价 | 建议 |
| --- | --- | --- | --- |
| 保留 A2 | 稳定对照、低依赖 | 词法弱项仍在 | 作为回滚与对照保留 |
| D：数据库内 BM25 | 复用事实平面与事务边界 | PG17、扩展依赖、按部门复制索引 | 已选生产实现 |
| 离线 Python BM25 | 算法验证、小型可控实验 | 上线需另建权限同步和增量索引 | 保留参考用途 |
| 独立搜索服务 | 支持独立扩缩容和额外全文搜索需求 | 双写/CDC、一致性、权限过滤、部署与回滚 | 规模或需求有证据时再评估 |

BM25 是算法，D 是一种实现。倾向数据库方案的原因是现有 PostgreSQL 已承载版本、ACL、审计和数据治理。组件版本、传递依赖和许可证在实际部署前仍须重新核查并锁定。

### 4.4 实施步骤

1. **已完成：** 固定文档版本、chunk UUID/哈希、向量、分词、词典、停用词、候选数、融合及重排版本；新 `retrieval_version` 为 `19c755…e4d1`。
2. **已完成：** 不依赖 RLS 隐藏统计。MA/PV/CO 使用三张表和三个 BM25 索引，共享文档按 read ACL 复制；草稿/撤回文本不入统计；撤权触发器在 ACL 事务中同步删除旧部门副本。
3. **已完成：** PostgreSQL 16→17 逻辑迁移。三个数据库恢复前后 Alembic、表、逐表行数、语料指纹和授权完全一致；随后升级 0022 并重建索引。旧 PG16 卷与三份带哈希 dump 保留。
4. **已完成：** 生产装配、outbox、覆盖检查、复合版本、Docker Compose 与 CI 改用 BM25；本机正式库与安全库 readiness 均为 true。
5. **待付费授权：** 在新冻结集上跑 BM25 的完整检索与回答、安全、费用和 P95 对照；历史对照只作为先验证据。
6. **后续组合实验：** 分别测 Redis、并发、裁剪，再与 BM25 组合，避免把组合收益错误归因给一个组件。

官方仓库说明 BM25 统计包含 RLS 隐藏行，支持这项风险需单独验证：[pg_textsearch 官方说明](https://github.com/timescale/pg_textsearch#row-level-security)。实际结论须基于本项目锁定版本。

### 4.5 验收与停止条件

- 权限、历史窗口、完整性、候选数和连接复用全部保持；部门间统计侧信道由物理语料隔离消除。
- 报告总体及中文药名、剂量单位、否定、方案编号、长上下文切片；旧门禁和新提议判据分开记录。
- 迁移/回滚可复现；扩展与镜像固定；复用共享装配，避免复制完整问答链路。首次本机迁移已经完成，部署手册保留步骤。
- 隔离成本不可接受、迁移复杂度超过收益或完整链路收益不稳定时，结束该候选并保留证据。
- 原 ADR 重测触发为语料扩大一倍以上或 Recall@5 失守；“简化补偿链路”是本文的新研究建议，不能称为已获得原 ADR 批准。

## 5. OPT-08 Redis 缓存

### 5.1 目标与现状

目标是降低重复问题的检索耗时，保持权限、版本与新文档可发现性。组件已接入 API，默认关闭，同问题/同权限/同版本才可能命中。

记录 121 的 120 题本机实验中，三种路径的候选、证据、顺序与正文 120/120 一致。翻译关闭时，无缓存检索中位数 3.90 s，命中 0.043 s。这是检索阶段重复问题的成绩，不是完整 API 的 43 ms。

### 5.2 边界与选择

| 内容 | 建议 |
| --- | --- |
| 候选与重排顺序 | 延续已有缓存设计 |
| 证据有效性 | 每次命中仍按身份回查可见性、状态、日期和哈希 |
| 最终回答 | 当前实时生成与核验；未来若缓存回答，另行定义适用条件与失效规则 |
| 缓存键 | 保留问题、部门、权限、会话实体、as-of、历史标志、检索/策略版本与部门纪元 |
| Redis 故障 | 降级为未命中并记录指标 |
| memory | 用于单进程演示，跨进程失效能力与 Redis 分别说明 |

### 5.3 实施步骤

1. 明确部署模式、TTL 和连接健康检查，脱敏输出配置状态，不打印 DSN 或密码。
2. 将 `make cache-invalidate` 对应 outbox 消费纳入可靠 worker 或定时任务；记录积压、最老事件年龄、最后成功时间和错误数。
3. 覆盖发布、撤权、归档、撤回、版本及重排变更。回查能移除失效旧块，旧候选列表却不能自动发现新块，必须及时失效重搜。
4. 分别测试全新查询、重复查询、预先固定比例的混合查询、权限/版本变化；混合比例不冒充真实流量分布。
5. 报告命中率、命中/未命中 P95、完整问答 P95、模型调用数、费用、Redis 内存、淘汰和失效滞后。
6. 有击穿证据后再加入同键合并请求、有限等待和限流；不同权限或版本的计算结果必须隔离。

### 5.4 验收

冷/热结果语义一致；撤权后不得返回不可见证据；新文档在事先约定的失效时限内可发现；Redis 故障可回源；消费者可幂等补消费。按工作负载报告收益，不把纯热缓存结果外推到全部请求。

### 5.5 2026-10-09 实施结果

主运行配置已设为 Redis，使用 `medops:local:v2:rcache:`；safety 清账使用独立前缀。Compose 常驻 worker ACK 主库 338/338 条历史事件，safety 一次性 ACK 339/339，均无失败或死信。Redis 断连时缓存入口降级为 miss，恢复后 Redis 与 worker 均回到 healthy。启用 Redis 时，超过 300 秒的缓存事件积压或死信会阻塞 readiness；关闭时仍只告警。

零模型 smoke 的 miss/hit 分别为 7.61/1.14 ms，只证明共享接线。CACHE-10 仍需用真实问题流量测量命中率、完整问答 P95、质量、Token 和费用，结果出来前不宣称性能目标达成。完整证据见[记录 164](reviews/2026-10-09-implementation-164-redis-cache-cutover.md)。

## 7. OPT-10 模型路由

### 7.1 已有结论

路由已进入配置版本和操作键；判定模型仍为 gpt-6-sol。诊断候选将 general_qa、label_query 作答改为 gpt-6-luna，一轮 200 题 + 159 安全项：费用 −72.6%，总体成功率 0.710→0.640，差 −7.0 pp；label_query 下降 18.4 pp。

[记录 125](reviews/2026-10-06-implementation-125-model-routing-pilot-rejected.md) 已否决广泛路由和仅 label_query 候选。仿单查询包含精确数值、否定和条件，不能仅凭意图名称判断任务简单。两臂不是同负载实验，也不能从此次单轮时延推导模型固有速度。

### 7.2 后续建议

1. 保留框架和失败证据，暂停重复运行相同候选。
2. 有新模型、新输入方法或更窄任务提出可验证假设时重启。
3. 难度路由只能使用在线可得信号：意图、证据覆盖、数字/否定/多文档冲突等；不使用 gold 或事后正确性。
4. 小模型失败再回退大模型时，计入两次调用、排队、重试与验证成本；报告回退率。
5. 翻译、结构化提取、一般回答、核验分开评估，一次改变一类调用。更换判定模型需要独立校准，会影响质量测量过程。
6. 同时报每题费用、每道正确回答费用、覆盖率、P95、风险切片。模型自报置信度不能单独决定路由。

### 7.3 验收与停止

沿用已批准 spend 口径：费用至少降低 25%，总体质量下降不超过 1 pp，切片与安全要求保持，正式轮数遵守既有门禁。token、美元、时延分别报告。窄路由覆盖太低、回退抵消收益或关键切片持续下降时，结束该候选。

## 8. OPT-11 时延、并发与任务排队

### 8.1 瓶颈依据

记录 111 中，并发 4 的检索节点中位耗时 6.4 s，高于作答节点 4.1 s；并发 8 吞吐约 0.39 req/s，继续增加到 16 时 24/30 超时。单 worker 排 8 个 Skill 任务，最后一项等待约 100 s。

这些说明优先研究检索阶段与资源排队。BM25 的词法毫秒级节省有价值，但重排、查询翻译和生成仍占较大部分；不能仅凭词法速度预测整体达到 8 s。

### 8.2 优化次序

| 次序 | 操作 | 先回答的问题 | 主要约束 |
| --- | --- | --- | --- |
| 1 | 细化计时 | 查询改写、翻译、SQL、向量、复查、重排、生成、核验、排队各占多少？ | 分别统计等待与计算；各阶段 P95 不能直接相加当作总 P95 |
| 2 | 限流和背压 | 接收多少同时执行请求才不形成长队？ | 拒绝/重试响应须有稳定契约，不能伪装成无证据 |
| 3 | 复用模型和缓存 | 字典/模型是否每次加载，哪些输入确实重复？ | 沿用固定线程，避免重新触发历史 MPS 卡死 |
| 4 | 减少重复检索/打分 | 相同查询、相同候选是否在一问内重复处理？ | 保持结果集合、次序与版本，计量必须覆盖全部调用 |
| 5 | 有边界的并行 | 翻译等待能否与原查询检索重叠？ | 不共享一个不适合并发的数据库事务；每路正确绑定身份，失败分支可追踪 |
| 6 | 批处理或独立重排服务 | 批等待成本能否换取吞吐？ | 记录批等待、超时、队列长度；先用现有进程内批能力验证 |
| 7 | worker 数量调整 | 当前约束在数据库、CPU、GPU、模型 API 还是任务串行？ | 多 worker 可能复制模型并争抢同一 GPU，不能盲目加进程 |

推荐先落地准入上限、队列上限、超时和可观察的资源等待。具体上限依据目标机器测量，历史“并发 4 较稳”可作为试验起点，不是通用默认值。

2026-10-09 的首个工程切片已完成：远程查询翻译通过进程级 4 worker / 8 在途有界池与原始/改写检索及文档聚焦重叠，250 ms 无槽位时以可重试系统错误失败关闭；Trace context 跨线程保留。词法/向量仍共享身份事务，本地嵌入与重排仍共享 pinned 模型线程，未在缺少一致性设计时强行并发。详见[记录 165](reviews/2026-10-09-implementation-165-translation-retrieval-overlap.md)。

### 8.3 性能实验与验收

- 固定机器、模型、代码、策略、语料、索引、缓存模式及热身方式；随机或交错安排两臂，减少时段差异。
- 分报执行时间和含排队时间；报告 p50/P95、吞吐、错误率、超时率、重试和成本，失败行不从分母移除。
- 原目标仍是普通问答 P95≤8 s、复杂 Skill 执行 P95≤15 s；队列等待另列服务目标。
- 每级 30 题可以定位瓶颈；对接近阈值的结论，需要预先设计更稳定的重复测量和足够样本。
- 质量、安全和成本与时延同时回归。降低检索量、缩短上下文或减少核验，均属于策略变化，需要对应效果证据。
- Streaming 可单独改善首 token 等待体验，但须报告首 token 和完整核验完成时间；未经核验的内容如何展示必须有明确产品规则。

## 9. OPT-12 没有第二人工时的评测制度

### 9.1 可继续工作的范围

可以继续版本冻结、机械校验、回归与实验。冻结意味着内容固定可复现；独立复核意味着由不同人审阅，两者各自记录。现有 provisional 标签和基线双人要求不能通过增加模型裁判或由同一人改名来满足。

若长期确定只有一位维护者，建议写出新的单人复核政策，说明证据等级、允许发布范围、抽检与复核频率、争议处置及已知限制，再按该政策审议后续版本。政策修改不能追溯性地把旧数据描述为双人审核。

### 9.2 评测分层

| 层 | 负责判断 | 实施方式 | 限制 |
| --- | --- | --- | --- |
| 机械校验 | schema、哈希、页锚点、来源、版本、权限、数字单位 | 确定性程序与真实角色集成测试 | 只能证明规则覆盖的性质 |
| 自动语义复核 | 是否回答问题、是否被证据支持、有无遗漏/矛盾 | 固定 rubric 的模型判断或多路检查 | 模型之间可能共享错误，意见一致不等于独立人工结论 |
| 唯一人工复核 | 争议、关键医疗条件、来源身份、切分歧义 | 隐藏候选名称与旧决定，间隔一段时间复核并留痕 | 只能称单人重复复核 |
| 独立外部复核 | 高风险或对外承诺的结论 | 有资源时邀请合格的第二人 | 未完成时如实保留缺口 |

建议优先人工处理：模型与规则分歧、剂量/单位/否定、版本冲突、点名来源、跨块证据、无答案标签可能失效、候选新引入的失败。其余采用按部门、语言、文档类型、风险层的分层随机抽样，保存种子与抽样分母。

### 9.3 数据划分与防污染

1. 明确开发集、回归集、验收 holdout。开发集可以反复分析；回归集防止已知错误复发；holdout 限制调参暴露。
2. 以文档家族/产品/近重复内容分组切分，避免同一原文的不同问法和中英文孪生落入不同集合造成泄漏。
3. 当前主集已经反复用于候选分析，应如实记录暴露历史。后续新增 holdout 用于验证泛化，不能通过改名让旧集变成“未见测试集”。
4. 测试失败可以进入独立回归集；不能一边拿它修改提示，一边继续将它计为未见验收样本。
5. 模型生成题必须记录生成模型、提示、原文和时间；公开医学文档支持的结论与人工合成安全 fixture 分开统计。
6. 无答案题是相对于某个语料快照的判断。扩语料后发现答案时标记 stale、升版替换并保留旧题，不能让系统凭新增知识答对却被错误评判。

### 9.4 指标分母必须明确

| 指标 | 要表达的含义 | 必须同时记录 |
| --- | --- | --- |
| Recall@k | 检索到了多少规定 gold 单元 | 有 gold 的样本数、gold 集合、多 gold 聚合方式、unmappable 数 |
| Hit@k | 前 k 是否至少命中一个 gold | 与 Recall 分别实现；多 gold 时二者不一定相等 |
| 引用结构准确率 | 引用是否指向本次可见证据 | 不代表每条陈述在医学语义上正确 |
| 支持度/忠实度 | 陈述是否被所引用内容支持 | 裁判版本、rubric、分歧与人工抽检 |
| 作答成功率 | 在固定 rubric 下问题是否解决 | 弃答、错答、系统失败分别记录 |
| 弃答质量 | 无答案题是否正确弃答、有答案题是否误弃答 | 两个分母分开 |
| 安全指标 | 越权、注入、高风险等行为是否符合预期 | 直接泄漏与来源错误、未触发/not_exercised 分开 |
| 费用与延迟 | 请求在实际条件下消耗多少 | 全部调用、失败、重试、队列和缓存模式 |

## 10. OPT-13 来源、gold、切分与清洗

### 10.1 首要问题：点名来源

“依据 ICH 文件 X 回答”和“询问某类药物的一般信息”对证据来源的要求不同。使用其他文档中的相同句子可能语义相近，但不能自然满足点名来源要求。已知 ss-0090/0096 等失败，以及主集中 14 道他文档同句题，需要在同一规则下处理。

建议：

1. 将来源要求标注为显式指定、上下文指代或未指定；这是一项拟议 schema 扩展，需升版。
2. 用稳定文档身份和可审核别名识别来源，覆盖标题截断、品牌/通用名、修订号、罗马数字模块号和同名异版。
3. 先在调用者可见文档中解析；不可见或不存在的来源使用符合既有公开错误边界的响应，避免借错误文案披露受限文档是否存在。
4. 显式来源缺失或证据不足时按规则弃答/澄清；不得自动把其他产品或版本当作指定文档。
5. 不直接恢复记录 115 已发现会误伤的粗糙过滤。先用开发争议集校准来源解析，再做冻结集回归。
6. 修改 gold 只能基于原文与固定标注规则，由明确身份作出裁决；不能为了候选通过改 gold。

### 10.2 文本与标识符的区别

| 名称 | 含义 | 约束 |
| --- | --- | --- |
| query | 用户问题 | 原文保留；改写是派生输入 |
| rewritten query | 检索用的改写问题 | 不改变数字、单位、否定、时间窗口与标识符 |
| key_text | gold 所指向的原文关键证据 | 来自可定位来源，用于匹配/定位；不是查询关键词列表 |
| gold | 该题可接受的证据标注集合 | 应含来源和位置，表达必要的联合证据或可替代证据 |
| document_key/doc_id | 文档业务键与实例标识 | 与版本、家族关系一起使用，不能单靠标题字符串代替 |
| chunk_id/span | 检索块标识与其原页区间 | 需回到原页；重新切分会影响映射 |
| cache key | 缓存条目的身份与版本键 | 与 key_text 是不同用途 |

### 10.3 当前规则与改进方向

源码 [normalization.py](../src/medops/retrieval/lexical/normalization.py) 的 norm-v1 顺序为 NFC、CJK 间抽取空白处理、全角 ASCII 映射、微符号统一、白名单单位替换、空白折叠；保留上下标与圈号，不进行通用 NFKC 折叠，不统一大小写。改动这些规则必须版本化，避免数值和证据坐标漂移。

[chunker.py](../src/medops/ingestion/chunker.py) 的 v2 在归一化页文本上切分：目标 400 字符、通常上限 600、短尾阈值 120、长段向前查找子句边界 200 字符；不跨页；分号作为子句分隔参与超长段处理。这里是字符数，不是模型 token 数；section 是启发式标签，引用主要依赖页和 chunk。

这些参数是已有版本的工程取值，不能仅凭现在存在就认为最优。建议针对跨块条件、表格列标题、否定后半句、单位和版本说明开展小规模切分对照。候选包括标题感知切分、表格行与表头绑定、受控相邻块扩展或父子块检索，按证据完整性和代价选择。

[rewrite.py](../src/medops/retrieval/rewrite.py) 的改写当前最多生成 3 条查询：原规范化问题、可信会话实体扩展、版本化词表扩展；追加而不替换原有受保护内容，不能从用户文本生成 SQL/权限过滤表达式。这些边界应继续保持。

### 10.4 清洗与 gold 维护流程

1. 原 PDF/页图/抽取文本/归一化文本分层保存，保留来源、下载时间、hash 与抽取版本。
2. 检查乱码、重复页、页眉页脚、OCR 数字混淆、表格塌列、单位丢失和字符映射；不可靠内容标记低信任并进入复核。
3. 去重区分字节相同、内容近重复、同家族新版本。合法修订不能当垃圾重复删除；训练/验收拆分应按家族控制。
4. gold 覆盖足以回答问题的完整条件。对 rp-0121、rp-0200、rp-0238 等曾讨论的相邻块问题，应查询已有裁决与当前版本，未闭合才重新提出，不能默认旧事项仍未处理。
5. 同时需要两个块的答案表达为联合证据要求；两个等价位置可表达为替代证据。二者评分规则不同，不能简单把 gold 扩大成“命中任一即可”。
6. 切分升级产生新 chunker 版本、新映射及检索版本；旧冻结 gold 保留。跨块无法映射的旧题继续按原规则报告，不从失败分母删除。

验收至少包括：原页回溯、数字/否定/条件完整性、边界映射、文档家族泄漏检查、人工分歧记录、跨版本结果可比较。清洗好坏最终通过这些可验证性质体现。

## 11. OPT-14 会话与记忆

当前 API schema 接受 `session_id`，但 `routes/ask.py` 未据此读取会话实体；Harness 的 `initial_state` 默认实体为空。因此只能确认“存在字段和内部能力”，不能宣称完整多轮记忆已接通。

建议先明确产品需要：如果只做单轮证据问答，文档明确范围即可；若演示“这个药呢”“上一份方案”的追问，则需要完整接线。

实现步骤：

1. 明确会话归属，以认证主体与租户/部门边界验证访问；单独持有 session_id 不授予权限。
2. 保存有限的、带来源与更新时间的结构化实体：药品、方案、适应症、人群等；优先不保存无界聊天全文。
3. 新请求在可信服务端读取实体并传入 initial_state。当前消息明确指定的实体优先；歧义要求澄清。
4. 会话实体进入缓存指纹、trace 与回放上下文。回放必须知道当时用过哪些上下文。
5. 设置 TTL、删除入口、权限变化处理及并发更新规则；跨会话污染、提示注入和过期实体纳入测试。

先用现有 PostgreSQL 或有清晰持久化边界的存储完成小范围会话状态。只有明确存在跨长期文档记忆需求时，再评估向量记忆库；工具选择不应先于产品语义。

## 12. OPT-15 索引覆盖与就绪

记录 109 曾发生 257 份已入库文档约四天没有检索索引的问题。现有 `make index-build`、`make index-check` 和评测预检已减少这类风险；记录 137 已将 [ProductionRuntime.ready](../src/medops/api/runtime.py) 接入真实覆盖、active 空文档、版本与实际库一致性检查，并以只读事务、超时和 5 秒缓存限制开销。记录 138 为词法、向量、缓存分别提供持续消费者；记录 164 已部署缓存消费者并清空正式/安全库积压。缓存启用时，其超过 300 秒的积压或死信进入 readiness；词法和向量消费者的统一常驻部署与毒事件实演仍待完成。

建议建立明确状态：已下载→已抽取→已摄取→质量放行→索引完成→可检索。active 数量、可检索数量和未完成任务分别可见。

实施方案：

- 在摄取/发布链路记录索引覆盖、词法/向量版本与最近成功时间，失败任务有可重试身份。
- readiness 读取轻量的最近检查状态，必要时设置最大状态年龄；避免每次健康探针都扫描全部 chunks。
- 明确新文档未索引时是阻止新版本成为 ready、使对应功能降级，还是允许带明确范围继续服务，选择写入契约。
- 检查结果绑定语料与索引版本，防止旧“全覆盖”状态在语料变更后继续被使用。
- outbox 索引与缓存消费者分别确认；“数据库可连接”“模型已加载”“索引覆盖”“消费者正常”分别显示。

验收场景：新增 active 文档却未建索引、索引版本漂移、消费者停止、恢复重试和部分构建失败。既有健康接口契约若需要变化，应同步 API、部署与测试。不能仅以文件下载存在代替可检索证明。

## 13. OPT-16 受控 Loop

当前 adapt 能自动形成部分检索参数候选；prompt/rule/skill 可能标为 `needs_author`。运行时实际支持的发布目标是 `retrieval_params/hybrid`、`prompt/answer_system`、`model_route/answer`。生成了候选文件与生产能执行该候选，是两个独立完成条件。

建议建立能力矩阵：可观察→可归因→可提出→可验证→可批准→可应用→可回滚，每一类候选逐格标证据。

后续只选一种高价值候选完成闭环，例如：知识缺口产生人工工单；或一个带明确参数边界的检索候选。确定性参数搜索适合可解释的小范围变化；模型建议适合草拟提示与规则，但仍需作者、约束校验和正式回归。

约束：

- 不用冻结 query/gold 直接生成针对测试题的补丁。
- 候选 diff 可读、基线版本明确，保持已经发布的其他参数，避免再次发生旧候选覆盖新策略的问题。
- 没有运行时实现的 target 在提交/发布边界明确拒绝或保持草稿，不给“发布成功但无效果”的假状态。
- 自动 Loop 继续只写候选或工单；批准和生产指针由既有受控流程管理。
- 证明有一条有价值的新闭环后再扩展类型，避免多个未接通的空壳节点。

## 16. 技术栈的选择逻辑与名词

| 名词/组件 | 含义与当前用途 | 同类选择与本项目判断 |
| --- | --- | --- |
| Harness | 管理执行状态、工具调用、重试、预算、约束与追踪的一层运行框架；本项目固定节点图外围还有执行账本 | 可用普通函数/状态机实现，也可依托图框架；保留当前已验证约束比换名字重要 |
| LangGraph | 表达 Intent→Retrieve→Verify→Safety→Answer/Escalate 的执行图 | 普通 Python 状态机适合更小流程；当前图结构和路径测试已有价值，无证据支持重写 |
| BM25 | 词法排序算法 | 与数据库或独立搜索服务组合；算法选择和部署选择分开 |
| 向量检索 | 用 embedding 寻找语义近邻 | 当前 bge-m3 + pgvector 复用事实平面；独立向量库增加同步责任，按规模再评估 |
| RRF | 用各路排名融合候选 | 避免直接相加不同量纲的词法/向量分数；权重或学习排序需额外校准数据 |
| Reranker | 对问题与候选内容进行更精细排序 | 质量收益与本机计算成本同时测；不能从模型存在推导吞吐足够 |
| Redis | 共享缓存存储 | 当前任务事实状态在 PostgreSQL；memory 适合单进程，Redis 提供共享缓存和纪元失效 |
| OTel / span | 追踪请求各阶段与属性的协议和记录单元 | 与后端选择解耦，保留脱敏边界 |
| Langfuse | 可用于 trace、评分、实验与人工复核的平台 | 先验证工作流和部署成本；Jaeger 可先覆盖调用链查看 |
| RLS | 数据库按身份限制可见行 | 应用过滤与数据库强制边界配合；还要单独检查排序统计侧信道 |
| Outbox | 与业务变更同事务写事件，再由消费者处理索引/缓存 | 异步消费需要积压、幂等与恢复观测；事务提交不代表外部更新已完成 |
| Gold / rubric | 标准证据标注 / 判断答案质量的明确规则 | 要有来源、版本、裁决与分歧，不能只放一段参考答案 |
| Provisional / frozen | 证据完成程度标签 / 内容固定状态 | 可同时存在，不代表数据无用或已经独立审核 |
| Ablation | 每次去掉/替换一个部件的对照 | 用来区分 BM25、翻译、词表、文档聚焦等各自收益 |
| pp / CI | 百分点差 / 置信区间 | 85%→87% 是 +2 pp；区间反映所用采样假设下的不确定性 |

## 19. 实验与验收记录模板

每项未来实施建议使用以下记录，便于开发、复核与面试复盘：

```text
Goal / 对应基线任务：
当前状态与证据路径：
要解决的用户问题：
假设与替代方案：
本次唯一变化 / 保持固定的项：
代码 commit 与未提交差异摘要：
语料、数据集、索引、模型、提示、策略、rubric 版本：
权限身份与缓存/历史日期条件：
样本量、抽样种子、分组、轮数、成功与失败分母：
质量、安全、覆盖率、时延、费用指标：

```

最终建议：把“能运行、能解释、能测量、能拒绝错误改动、能恢复”做扎实。BM25、缓存、观测与路由都有各自的价值，但交付顺序和是否采用，应由这个项目中的真实问题与可复现证据决定。
