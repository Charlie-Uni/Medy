# S2 最小澄清续办

任务：SESSION-01/02 的 S2 子范围；依据 [PLAN-02 §4.3](PLAN-02-action-budget-and-acceptance.md)与[ADR-0012](../adr/ADR-0012-agent-evolution-goals-and-acceptance.md)。完整多轮实体记忆、五类业务和对话 UI 仍在 S4。本轮实现及限制见[记录224](../reviews/2026-10-19-implementation-224-agent-clarification-continuation.md)。

## 1. 身份与生命周期

```mermaid
flowchart LR
    A[原执行：awaiting_clarification] --> B[保存的问题与材料]
    B --> C[用户显式补充并提交续办命令]
    C --> D[同一个 case_id；新的 task/run/attempt/trace]
    D --> E[重新检索、规划与最终核验]
```

原执行保持终态、步骤、调用回执、费用和绝对截止时间；不能通过 `recover()` 继续业务。新执行从自己的新期限开始，仍受八步、12,000 Token、0.60 USD、125秒及最终核验预留保护。新执行重新解析指定文档/版本；历史日期与显式历史模式不变。旧 evidence handle 不移入新执行，必须在新绑定下重新获取、引用和核验。

材料来自原来的加密 Agent journal。新建三张表仅保存身份、关系、摘要、计数、期限及费用，不复制叙述、答案、指南正文或提示。新执行中，原叙述保留；非来源字段的补充标记为用户输入，不能作为已核验事实。只允许回答原终态保存的问题且属于已登记的 `clarifiable_fields`。指定文档、版本各自校验原字段长度；叙述合并超过4,000字符会拒绝，不能截断。

## 2. 必填运行配置与授权

`ClarificationPolicy` 三项都必填：

| 字段 | 含义 |
| --- | --- |
| `ttl_seconds` | 从原执行开始时间计算业务有效期；再次打开不延长 |
| `max_continuations` | 同一 case 的续办次数上限，跨授权批次也不清零 |
| `cost_limit_microusd` | 同一 case 的累计费用上限，包含原执行与各次续办 |

`ContinuationAuthorization` 必须来自可信服务端，提供批次 UUID、实际批准记录的摘要、允许的 case UUID 列表、截止时间、执行次数与费用总上限。当前没有获准的产品默认 TTL、次数或总费用。测试中的数值只属于公开合成夹具。数据库有一条 grant、旧授权剩余额度或调用者传入摘要，都不能替代所有者对本轮付费实验的实际授权。

批次控制的是这一次新批准的续办范围。原执行在它原有授权下已经产生的费用只计入 case 汇总，不伪装成新授权批次的新增支出。使用同一个批次跨 case/新 task 执行时，共用数据库中的次数和累计额度；若以后取得新的明确授权，case 的总次数/总费用上限仍保留。

## 3. 服务端接口

入口是 `production_agent_continuation(...)`，必须显式传 PlannerConfig、FinalGateConfig、事实库绑定、rubric 摘要与租约。它使用生产 Agent Runtime、当前身份目录、真实来源解析及最终业务核验。它是可信服务端 API，尚无公开 HTTP 启动端点、UI 自动续办或定时重试。

| 操作 | 行为 |
| --- | --- |
| `open_case(source_run_id, policy, authorization=...)` | 认证原用户，读取并验证原澄清终态；保存稳定 case 与原执行费用 |
| `authorize(grant, authorization=...)` | 登记已经实际批准的批次；同一 ID 不可换额度、期限、次数或范围 |
| `case(case_id, authorization=...)` | 读取当前用户自己的无正文状态及费用汇总 |
| `continue_case(source_run_id, command, authorization=...)` | 显式回答问题、校验修订号、预留额度、创建并执行新 run |
| `executions(case_id, authorization=..., after_ordinal=-1, limit=32)` | 按稳定序号分页读取各执行的关联与已知/保守/预留费用，每页最多64条 |
| `delete(case_id, expected_revision=..., authorization=...)` | 保存不可复活的删除标记，阻止后续动作与结果交付 |

`ContinueAgent` 只有命令 UUID、授权批次 UUID、期望修订号、问题字段与补充值，不能传入身份、预算、模型、步骤或已完成结果。命令 UUID 稳定导出新的 task/run/attempt/trace；服务端保持原 case ID。命令与来源 run、补充内容、期望版本和批次摘要绑定。

## 4. 预留、失败与取消

启动前先锁授权批次，再锁 case，检查当时数据库时钟、当前身份/部门/read scope、删除、来源 run、修订号、case 次数/费用及批次次数/费用。为整个新执行预留0.60 USD，提交成功之后才能开始 Agent。即使本次预计只问一个问题，也不能用估计费用降低保守预留。

持久执行控制层的`claim/renew/fence/assert_owned`也调用同一case守卫，进程重建不能丢失TTL/删除/已预留运行的约束；旧schema及未登记case保留原Agent控制语义，已登记case没有匹配预留时不能启动。账务清理及已封闭结果读取不使用运行中的case守卫。

每次模型调用和业务终态提交前再次核对登录身份、case 当前 run、TTL、删除状态和授权期限。删除/撤权可以阻止后续调用与正文交付；已经进入外部提供商的调用仍可能收费，费用审计和财务清理继续保留。

已知金额来自原子保存的业务 Trace；`accounted - known` 是未知 usage 的保守部分，`held` 是尚未确认的整轮预留，三者不能混称实际供应商账单。测试夹具显式模拟每次0.001 USD回执来验证累计；实际没有托管调用或真实支出。

只有真实终态已提交、费用已完整核对，才释放剩余额度并把本次计费加入 case/batch 汇总。未知 usage 继续使用原预算系统的保守计费。启动/提交结果不确定时保留整个预留与占用的命令，不能因为换进程、换 task 或重试而重新获得额度。

相同命令且已结算时只读结果，不新建 root，不调用模型。相同 UUID 配不同输入拒绝；同一来源只能有一个后继。未确认完成的命令不会自动重开，暂需后续受控核对处理；该保守策略可能占住本来未花完的额度，但不重复收费。

## 5. 隔离、删除与可追溯

三表启用并强制部门 RLS；应用层额外核对原用户及完整当前身份，管理员不能借角色继续另一个人的业务。UUID、revision 与表约束负责持久命令占用；短事务和行锁负责并发排他；读取 case 修订号与费用汇总时也持有同一 case 行锁，避免混合新旧状态。模型只提出业务动作。

新 run 在第一次模型调用前提交 `clarification_continuation` 加密 checkpoint，保存 source run、case、command、batch 与请求摘要；原材料和本次运行分别保留。新终态沿用 Agent 的原子保存、业务 Trace 和反馈路径，费用按执行和业务 case 两层统计，不能只留下最终成功的一次。

“删除”指撤销该业务 case 的可继续使用状态；不是越过既有审计保留政策立即抹除调用、账务与加密原材料。删除不会恢复 TTL、删除原终态或释放不确定费用；有合法当前权限的原有审计接口仍按自身保留契约工作。物理清理/保留策略、完整多轮遗忘和 UI 交付另验收。

## 6. 本轮验证范围与限制

工程测试使用临时真实 PostgreSQL、真实应用角色/RLS/事务/加密、真实生产装配和离线 Fake 提供商；无托管模型费用。覆盖正向续办、旧执行不变、身份/部门/跨 case、过期/删除/撤权、修订号竞争、重复命令、预算/授权范围及不确定启动等反例。详细命令、失败和复测结果写入记录224及结果 JSON。

迁移0033只用于临时测试；正式三库仍0026，0027～0033未因此部署。工程通过不能证明真实模型完成率、性能、生产可用或盲测改进；仍需 AGENT-07 集成验收及 AGENT-08 本轮明确授权的真实试跑。

原执行结果读取仍采用已有当前身份/事实/策略版本保护。若旧终态已过保留期、版本不兼容或当前来源权限不满足，续办会失败关闭；不会为了续办重绑旧记录、复用旧核验或放宽历史条件。跨旧策略材料兼容迁移属于后续范围。
